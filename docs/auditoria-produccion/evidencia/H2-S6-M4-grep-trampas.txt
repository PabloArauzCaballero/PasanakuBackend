Clasificación de cada match (regla 80.4 — no se clasifica sin evidencia):

1. ci.yml:155 — `grep -q "FALLA" humo.txt && exit 1 || true`
   Bajo `set -e` (default de GitHub Actions para pasos `run:` en bash), si `grep -q`
   encuentra "FALLA", `exit 1` termina el paso ahí mismo — el `|| true` nunca llega
   a evaluarse en ese camino. Si NO encuentra "FALLA", `grep -q` devuelve 1 (sin
   match) y el `&&` corta antes de `exit 1`; el `|| true` solo evita que ESE exit
   code (ausencia de "FALLA", que es el caso BUENO) tire abajo el step. No tapa
   ningún fallo real: el fallo real (`FALLA` presente) sigue matando el step.
   LEGÍTIMO — no es una trampa.

2. boveda-y-esquema.yml:145-146 — mismo patrón: `grep -c ... || true` para poder
   capturar un conteo de 0 sin que `set -e` mate el script por el exit code de
   "no match" de `grep -c`. El fallo real se decide después, explícitamente, con
   `if [ "$fallas" -ne 0 ]; then ... exit 1; fi` (línea 147 en adelante) — no está
   escondido detrás del `|| true`. LEGÍTIMO — no es una trampa.

3. boveda-y-esquema.yml:57 — no es código: es la propia explicación en comentario
   de por qué el paso de H2.S6.M3 NO usa `|| true` (contiene el string literal
   entre backticks como ejemplo). Falso positivo del grep sobre un comentario.
