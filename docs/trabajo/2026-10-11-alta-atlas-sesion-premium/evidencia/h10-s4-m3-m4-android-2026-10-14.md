# H10.S4.M3–M4 — protección de captura y limpieza temporal en Android

Fecha: 2026-10-14. Ejecución serial en el AVD Samsung_A06-L, dispositivo `emulator-5554` (Android virtual x86_64, API 33). Sin backend ni datos personales.

## H10.S4.M3 — protección de pantalla del sistema

Comando:

```text
cd apps/movil
flutter drive --no-pub -d emulator-5554 --driver=test_driver/h10_s4_m3_m4_privacidad_test.dart --target=integration_test/h10_s4_m3_m4_privacidad_test.dart
```

La prueba montó `PantallaDeSesion`, la fase de cuenta de `PantallaDeRegistro` y su fase de identidad/documento. Un observador sincronizado con los marcadores consultó `dumpsys activity activities` y capturó mediante `adb exec-out screencap -p` en cada ventana:

| Etapa | Actividad en primer plano | Bytes entregados por `screencap` | Salida ADB |
|---|---|---:|---:|
| `LOGIN` | `bo.aportaya.aportaya_movil/.MainActivity` | 0 | 0 |
| `ALTA_CUENTA` | `bo.aportaya.aportaya_movil/.MainActivity` | 0 | 0 |
| `ALTA_IDENTIDAD` | `bo.aportaya.aportaya_movil/.MainActivity` | 0 | 0 |
| `CAMARA` | `bo.aportaya.aportaya_movil/.MainActivity` | 0 | 0 |

En contraste, `screencap` en el launcher fuera de la app entregó 558.205 bytes; esto descarta que el comando estuviera globalmente roto. Las cuatro salidas vacías se conservaron como artefactos `h10-s4-m3-*-foreground-2026-10-14.png`; no contienen píxeles para inspección visual. El código nativo activa `WindowManager.LayoutParams.FLAG_SECURE` mediante el canal de privacidad y las pantallas montadas invocan ese puerto.

La primera integración protegió login/cuenta/identidad y pasó **3/3**. Se amplió después para abrir la pantalla real `PantallaDeCamara` sobre el registro ya protegido; la captura sincronizada encontró `MainActivity` en primer plano y 0 bytes. Esa repetición también pasó **3/3** (`00:54 +3: All tests passed!`). El visor de cámara del caso H10 usa una vista sintética para aislar `FLAG_SECURE`; un intento con el proveedor de cámara Android no inicializó en ese harness. La cámara real tiene prueba CameraX separada, 1/1, en [H5.S4.M3](./h5-s4-m3.txt). No se tomó ni guardó ninguna foto. El bloqueo de captura del sistema queda `HECHO` en AVD; no equivale a validación en teléfono físico.

## H10.S4.M4 — limpieza del directorio temporal

En la misma integración, ya dentro del proceso Android, `Directory.systemTemp` contenía cinco archivos `.jpg` sintéticos. El flujo real `SubidaNotifier.subirPendientes` llamó cinco veces al proveedor `SubidaDeFotos`; el sustituto verificó que cada archivo existía antes de responder con éxito. Al finalizar, el directorio temporal real del emulador quedó vacío:

```text
H10_S4_M4_FILES_BEFORE=5 AFTER=0
00:54 +3: All tests passed!
```

Esto verifica la limpieza de archivos del filesystem Android al completarse la subida. La red/subida remota fue simulada: no se usó backend, una foto real ni un documento personal. El criterio de limpieza local de M4 queda `HECHO` con este alcance explícito.

## Recursos

El AVD Samsung_A06-L se inició y apagó de forma explícita; la integración se ejecutó serialmente. Durante el último recorrido quedaron aproximadamente 2,38 GiB libres; tras apagar el AVD y Gradle volvieron a quedar ~7,14 GiB. No se inició Docker.
